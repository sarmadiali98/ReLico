# ReLico User Workflow Guide

`scripts/relico` is the reviewer- and user-facing entry point for anyone who has
a Timed Rebeca (DTR) model and does not want to learn the internal repository
layout. It is a thin wrapper over the same verified pipeline stages the
benchmark corpus and `scripts/reproduce.sh` drive — it adds no pipeline logic
and no new semantics. Tool discovery (`java`, `maven`, `lake`, `lfc`, the RMC
jar, and the parser archive) and the `RELICO_*` overrides behave exactly as they
do for the benchmarks.

Nothing is written into the repository; all artifacts land under an output
directory (default: a fresh `/tmp/relico-workflow.<timestamp>/`, override with
`--out`).

## Subcommands

### `scripts/relico analyze <model.rebeca>`

Accepts the model, reports the supported fragment, and validates priorities.
It parses and decodes only — no external model checking or compilation.

```bash
scripts/relico analyze path/to/model.rebeca          # human-readable report
scripts/relico analyze path/to/model.rebeca --json   # machine-readable report.json
```

### `scripts/relico run <model.rebeca>`

The full workflow: analyze, then DTR (RMC) model checking, translation to
Lingua Franca, `lfc` compilation, and a short runtime, ending in a clear report
and a machine-readable `report.json`.

```bash
scripts/relico run path/to/model.rebeca
scripts/relico run --with-runtime path/to/model.rebeca   # also execute the native binary
```

## Example outputs

Two sanitized reports and one generated LF artifact are committed in this
directory so you can see the report shape and a translation result without
running the pipeline. Absolute paths are replaced with `<OUT>`/`<REPO>`
placeholders and volatile timestamps and durations are normalized, so the
committed files are deterministic.

| File | Command | Verdict |
|---|---|---|
| [`smarthome-analyze.report.json`](smarthome-analyze.report.json) | `analyze` on the smart-home case study | A |
| [`causal-msgsrv-chain-run.report.json`](causal-msgsrv-chain-run.report.json) | `run` on the causal-msgsrv-chain benchmark | A |
| [`causal-msgsrv-chain.lf`](causal-msgsrv-chain.lf) | LF source generated by that `run` | — |

### Report structure

Every report is a single JSON object. The top-level keys include:

- `command` — `analyze` or `run`.
- `verdict` — the overall verdict (`A` = all attempted stages passed).
- `model` — the input `name`, `path`, `sha256`, and `size_bytes`.
- `supported_fragment` — `status` (`PASS`/`FAIL`), the `detected` constructs,
  and the `fragment_boundaries` the model stays within.
- `priorities` — `status`, plus the derived `actor_routing_order` and
  `message_server_order` (reaction-declaration order) and any `issues`.
- `model_checking`, `translation`, `lf_compilation`, `runtime` — per-stage
  `status` with `PASS`, `FAIL`, or `SKIPPED`, plus a short `detail`. `analyze`
  reports the pipeline stages as `SKIPPED`; `run` populates them.
- `stages` — the ordered list of stages actually executed. For `analyze`:
  `accept`, `parse`, `decode`. For `run`: `accept`, `parse`, `decode`,
  `model-check`, `translate`, `compile` (and `run` with `--with-runtime`).
- `tool`, `relico_version`, `schema_version`, `started_at`, `finished_at`,
  `output_directory` — provenance metadata.

For example, the committed `run` report records model checking and compilation
succeeding:

```json
"model_checking": {
  "detail": "Deadlock-Freedom and No Deadline Missed = satisfied",
  "status": "PASS"
},
"lf_compilation": {
  "detail": "lfc 0.11.0",
  "status": "PASS"
}
```

and the generated `causal-msgsrv-chain.lf` is the Lean translation output for
that model, targeting `Cpp` with one `Node` reactor whose message servers become
logical actions and reactions.

## Relationship to the other entry points

- [`../../smoke-test.sh`](../../smoke-test.sh) drives `scripts/relico` over a
  tiny bundled model as a fast six-gate confidence check.
- [`../../scripts/reproduce.sh`](../../scripts/reproduce.sh) reproduces the full
  evaluation using the same pipeline stages.
- [`../../ARTIFACT.md`](../../ARTIFACT.md) is the top-level reviewer walkthrough.
